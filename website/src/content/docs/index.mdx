Hundreds of end-to-end tests pass, but pgSaci has never run a real workload.

## What it is

pgSaci speaks Oracle's **TNS / TTC wire protocol** on the front and **stock
PostgreSQL** on the back. An unmodified Oracle client — `python-oracledb` (thin),
the Oracle JDBC thin driver, ODP.NET managed — points at pgSaci instead of at an
Oracle database, and pgSaci:

<CardGrid>
	<Card title="1 · Terminates the handshake" icon="seti:default">
		The full Oracle Net connect + TTC negotiation + challenge/response auth
		(12c PBKDF2 with mutual server proof, or the 11g MD5 verifier).
	</Card>
	<Card title="2 · Translates the SQL" icon="seti:sql">
		The Oracle SQL/PL-SQL dialect it understands is rewritten to PostgreSQL
		SQL; binds are sent as PostgreSQL parameters.
	</Card>
	<Card title="3 · Runs it on PostgreSQL" icon="seti:db">
		One backend round trip to an ordinary current PostgreSQL release with the
		<a href="https://github.com/orafce/orafce">orafce</a> extension.
	</Card>
	<Card title="4 · Re-frames the result" icon="seti:binary">
		The PostgreSQL result is re-encoded into Oracle's binary framing and
		streamed back batch by batch.
	</Card>
</CardGrid>

The application keeps its Oracle driver, its connection-string shape, and most
of its SQL. Nothing about the database it actually talks to is Oracle.

## How this differs from IvorySQL

[IvorySQL](https://github.com/IvorySQL/IvorySQL) is a **fork of the PostgreSQL
server** that builds Oracle SQL / PL-SQL compatibility — an Oracle parse mode,
PL/iSQL, packages, `NUMBER`/`DATE` semantics — into the engine. It goes deep on
the *dialect*, but it still speaks the **PostgreSQL wire protocol**: the
application connects with a PostgreSQL driver, not its Oracle one.

pgSaci is the other way round. It speaks Oracle's **TNS/TTC wire protocol**, so
the unmodified Oracle driver — ojdbc, ODP.NET, `python-oracledb` — connects to it
exactly as it would to Oracle, and the database behind it is stock PostgreSQL.
The trade is the SQL/PL-SQL surface: pgSaci only covers what its translation
layer plus `orafce` can express.

They solve different problems. Reach for IvorySQL if you can repoint the app at a
new database and want broad Oracle SQL semantics; reach for pgSaci if the app and
its Oracle client have to stay exactly as they are.
